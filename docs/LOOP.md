# LOOP — журнал опыта и улучшений

Цель: фиксировать положительный и отрицательный опыт разработки сайта и интеграции с SaaS, чтобы не повторять ошибки и ускорять следующие шаги.

## Формат записи

Каждая запись содержит:

- **L — Log:** что сделали и в каком контексте;
- **O — Outcome:** фактический результат;
- **O — Optimization:** что нужно изменить в процессе или архитектуре;
- **P — Prevention / Practice:** правило, тест или автоматизация, которые закрепляют вывод.

## Обязательные правила

1. Не заявлять, что процесс, ветка, API, CI или деплой готовы, пока это не проверено инструментом.
2. Перед созданием ветки, файла или PR проверять существование объекта.
3. Не включать шумный CI на каждый коммит до прохождения одного ручного контрольного запуска.
4. Сайт не дублирует CRM: каталог и захват спроса остаются на сайте, компании, контакты, заявки и стадии — в SaaS.
5. Любая интеграция сайта с SaaS должна использовать версионированный контракт, idempotency key, журнал событий и безопасный server-to-server вызов.
6. После каждого сбоя фиксировать первопричину, исправление и защиту от повторения.
7. Положительный опыт также фиксировать как повторяемый шаблон, а не только как описание успеха.

## Записи

### 2026-07-30 — поток уведомлений GitHub Actions

**L — Log**  
Проверки качества сайта запускались после частых коммитов и создавали повторяющиеся письма о сбоях.

**O — Outcome**  
Процесс создавал шум и мешал отличать важные ошибки от повторных уведомлений.

**O — Optimization**  
Сначала выполнять ручной контрольный запуск, затем включать автоматический триггер только после стабильного прохождения.

**P — Prevention / Practice**  
До стабилизации workflow использовать `workflow_dispatch`; автоматический запуск возвращать только после успешной проверки конфигурации и тестов.

### 2026-07-30 — неподтвержденная ветка SaaS

**L — Log**  
Было заявлено создание ветки `feat/public-website-intake`, но последующая проверка через поиск веток не дала результата; попытка повторного создания вернула `Reference already exists`.

**O — Outcome**  
Фактическое состояние нельзя определять по одному косвенному ответу инструмента.

**O — Optimization**  
Проверять ветку прямым чтением файла по ref либо через метаданные репозитория и только после этого описывать статус.

**P — Prevention / Practice**  
Не использовать формулировку «создано» без подтверждаемого SHA, ref или доступного файла в этой ветке.

### 2026-07-30 — каталог как часть воронки

**L — Log**  
Каталог, поиск, товарные интересы и форма заявки связаны единым пользовательским сценарием.

**O — Outcome**  
Сайт начинает передавать в SaaS не только контакт, но и контекст намерения покупателя.

**O — Optimization**  
Продолжать сохранять `sessionId`, UTM, поисковые запросы, просмотренные категории и выбранные позиции в одном payload.

**P — Prevention / Practice**  
Добавлять контрактные тесты на соответствие фронтенд-payload и SaaS intake endpoint при каждом изменении схемы.

### 2026-07-30 — единый источник данных каталога

**L — Log**  
Для каталога и отдельных страниц товарных групп создан общий файл `catalog-data.js`, вместо независимого дублирования списков продукции.

**O — Outcome**  
Каталог и посадочные страницы используют одинаковые названия, описания, примеры и стандарты; добавлена возможность перехода из карточки группы на подробную страницу без потери контекста SaaS-воронки.

**O — Optimization**  
Следующим этапом вынести данные из JavaScript в управляемый источник контента или API, когда объём реальных позиций станет слишком большим для ручного файла.

**P — Prevention / Practice**  
Не создавать второй независимый список товарных групп. Любая страница, SEO-шаблон или форма должна получать данные из единого источника и проверяться тестом на корректный `productGroupId`.
